# 框架与架构选择门

本参考把“是否需要调研”和“什么时候需要反方审查”变成可执行的工程路由。它不要求所有任务都调研，也不把反方审查变成无边界的重新设计。

## 先判断任务类型

| 场景 | 默认路径 |
|---|---|
| 只是讨论候选框架，没有承诺采用 | 约束澄清与轻量比较；不必立即建立研究文件 |
| 已有稳定框架和实现模式，只做局部改动 | L0：核对当前版本、入口和项目约定 |
| 新框架、新版本、新扩展或外部运行时 | L1：定向事实核对 |
| 方案依赖生命周期、状态、权限、恢复、并发或副作用行为 | L2：最小可行性 Harness/Spike |
| 选择基础框架、替换运行时或锁定长期架构 | L3：选择级调研 + 独立反方审查 |

## 调研触发谓词

将以下条件当作路由判断，而不是机械清单：

```text
research_required =
  new_or_unknown_framework
  OR version_or_api_is_stale_or_conflicting
  OR runtime_state_permission_recovery_is_material
  OR external_side_effect_or_concurrency_is_material
  OR choice_changes_cost_security_lock_in_or_maintenance
  OR current_architecture_claim_lacks_real_evidence
```

如果全部为假，直接引用当前项目事实；如果只有一个局部事实未知，做 L1；如果未知事实可能推翻方案，做 L2；如果正在选择长期基础框架，做 L3。

## 调研任务契约

```markdown
### research-<topic>-<id>
- 问题：要确认的单一问题是什么？
- 范围：版本、目录、运行入口、外部来源和不调查的范围
- 权威来源：官方文档、当前源码、配置、真实运行探针或一手 API
- 已确认事实：
- 本地观察：
- 假设：
- 未验证：
- 对架构候选的影响：
- 下一步：继续设计 / 做 Spike / 限定范围 / 暂停
```

调研输出事实和证据，不直接替用户做产品取舍。短期事实可以放项目研究文档或 `findings.md`；长期框架选择和取舍写入 `decisions.md`，不要把一次研究结果伪装成永久规则。

## 反方审查契约

反方审查在以下情况触发：

- L3 框架选择或基础架构提交；
- 状态、权限、恢复、并发或外部副作用的结构性变更；
- 关键依赖的源码、文档与本地运行结果不一致；
- 方案声称可恢复、可重试、可扩展或可接管，但尚无直接证据。

审查使用新鲜上下文、最小权威材料和当前版本证据。每条 Finding 按以下格式记录：

```markdown
### F-<id> [Blocker|Major|Minor]
- 违反的要求或假设：
- 失败条件：
- 影响：
- 证据：
- 建议：
- 处置：Accept / Reject / Defer
- 返回门禁：Q1 / Q2 / Q3 / Q4 / 无
- 重新验证条件：
```

`Blocker` 或影响核心行为、数据、权限、恢复的关键 `Major` 会阻止当前范围放行；普通优化可以被有依据地拒绝或延后。反方审查发现问题后，执行“修正 → 定向复审”，不默认重做所有门禁。

## Pi Agent 示例

如果任务要基于 Pi Agent 开发：

1. Q1 从 PRD 提取依赖 Pi Agent 的能力，例如 Session 恢复、工具注册、Subagent、权限或后台任务。
2. 若当前版本、扩展接口或状态行为没有可靠事实，至少做 L1；若方案依赖真实生命周期和恢复，则做 L2。
3. 如果任务是在 Pi Agent 与其他运行时之间做长期选择，进入 L3，并把候选比较和反方 Finding 写入决策前材料。
4. Q2 只依据调研事实设计模块、状态、数据所有权和验证入口；未验证能力只能限定范围。
5. Q4 用真实入口核验，不以扩展可加载、Mock 通过或单元测试通过替代产品级验证。
