# 用户状态与决策边界

质量闭环需要让用户理解当前处境，同时保留用户对产品目标和重要取舍的判断权。状态展示不是原始日志转发，也不要求用户参与普通工程步骤。

## 状态卡

在任务启动、阶段切换、阻塞、范围变化和收尾时，按需展示：

```text
当前阶段：Q1 / Q2 / Q3 / Q4 或具体节点
当前状态：进行中 / 已完成 / 部分完成 / 受阻 / 未验证
已确认与关闭证据：
未验证、阻塞与责任：
需要用户思考：无 / 具体决策及影响
推荐路径：
下一步与停止条件：
```

状态卡只保留会影响行动的内容，不逐条列出工具调用。事实、推论、推荐和用户决策要分开写，不能把推论写成已确认事实。

## 何时由用户判断

| 问题类型 | 默认处理 |
|---|---|
| 能通过文件、工具或运行检查查证的事实 | 执行者查证并报告依据 |
| 普通工程实现、修复顺序和测试选择 | 执行者在已确认范围内判断 |
| 目标、范围、成本、权限、上线标准或不可逆风险变化 | 交给用户确认 |
| 证据不足但不影响当前承诺 | 限定范围继续，并标明未验证 |
| 证据不足且影响核心承诺 | 暂停受影响范围，进入 `awaiting_user` 或补充验证 |

## 决策卡

需要用户决定时，给出一张具体决策卡：

```text
决策 ID：
当前事实：
可选路径：
推荐路径及原因：
每条路径的影响：
不作选择时的默认行为：
会影响哪些节点或已有关联证据：
```

只提出一至三个真正改变方向的问题。用户作出选择后，将选择、适用范围和影响写入现有 `decisions.md` 或项目当前决策文档，更新 `task_plan.md` 的范围，并让受影响节点重新准入；不要仅在聊天中保留决定。

## 用户反馈与流程改进

用户对“状态是否清楚、问题是否值得问、流程是否造成重复等待”的反馈属于流程观察。阶段有实质结果时写入 `changelog.md`；反复出现且影响后续判断的模式才提升到 `findings.md`。不为一次偏好建立永久规则。
